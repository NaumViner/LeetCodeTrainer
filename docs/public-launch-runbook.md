## 3. הכנת הקוד לשחרור

שורש מאגר Git שנבדק הוא `C:\Dev\leetCodeTrainer\v3`. זהו שורש האפליקציה במאגר `NaumViner/LeetCodeTrainer`; ב־Vercel משאירים Root Directory בשורש המאגר, ולא מוסיפים `v3`, כל עוד מבנה המאגר לא השתנה.

יש בתיקיית העבודה שינויים קיימים שלא בוצע להם commit, כולל מיגרציות. לפני הפריסה בודקים את הדיפ ומוודאים שהשחרור כולל את כל הקבצים הדרושים. Vercel שבונה מ־Git אינו מקבל קבצים שלא נכנסו ל־commit.

לפני שחרור מריצים מ־PowerShell בשורש האפליקציה:

```powershell
Set-Location 'C:\Dev\leetCodeTrainer\v3'
npm ci
npm run lint
npm run typecheck
npm test
npm run db:start
npm run db:migrate
npm run test:integration
npm run test:e2e
npm run build
npm run audit:client-bundle
npm run format:check
```

עוצרים ומתקנים אם אחת הבדיקות נכשלת. Docker נדרש למסד המקומי ודפדפן Playwright נדרש לבדיקות הדפדפן. המפתחות לבדיקות אוטומטיות הם מפתחות בדיקה בלבד. את בדיקת הקול האמיתית מבצעים בנפרד עם מיקרופון שהמשתמש בחר להפעיל.

חובה לבדוק גם שדרוג מסכמה קיימת וגם בניית DB בדיקה נקי מכל המיגרציות. איפוס DB מותר רק בסביבת בדיקה חד־פעמית שאומתה; הוא אינו חלק מהוראות Production.

## 4. Supabase: Database

יוצרים פרויקט Production ייעודי ושומרים project reference, כתובת API ומפתחות במקומות המתאימים. סיסמת DB ומפתחות ניהול נשמרים במנהל סיסמאות/סודות. בוחרים אזור לפי קהל היעד ומקרבים אליו את סביבת השרת ככל שהשירותים מאפשרים.

מבצעים תחילה את אותו תהליך בסביבת Staging. ב־Production מאמתים שהפרויקט הנבחר הוא הפרויקט הנכון, ואז:

```powershell
npx supabase login
npx supabase link --project-ref 'REPLACE_WITH_PRODUCTION_PROJECT_REF'
npx supabase db push --dry-run
```

בודקים שהרשימה כוללת את המיגרציות המצופות בלבד. לאחר סקירת התוכנית והכנת גיבוי מתאים אם כבר קיימים נתונים:

```powershell
npx supabase db push
```

כל הפקודות בסעיף זה הן לביצוע בשלב הפריסה, ולא הורצו כחלק מהכנת הקבצים. מיגרציות הן מסלול המקור לסכמה; לא יוצרים טבלאות Production רק דרך הדשבורד. [תיעוד מיגרציות Supabase](https://supabase.com/docs/guides/deployment/database-migrations).

לא משתמשים ב־`db reset --linked`. אין להעלות משתמשי בדיקה או תוכן זמני. אחרי העלאת הסכמה בודקים נושאים פעילים, מלאי שאלות מאושרות לטווחים המוצעים, RLS ופעולת RPC ליצירת ראיון אורח. עצם קיומו של קטלוג 150 שאלות אינו הוכחה שכל שאלה זמינה לראיון.

## 5. Supabase: Auth ואימייל

בהגדרות Auth מגדירים את כתובת האתר הקנונית ואת כתובת החזרה המדויקת:

```text
Site URL: https://YOUR_DOMAIN
Redirect URL: https://YOUR_DOMAIN/auth/callback
```

את Preview מחברים ל־Staging. אין להגדיר הרשאות redirect רחבות ל־Production רק כדי להקל על Preview.

מפעילים Anonymous Sign-Ins ו־Manual Identity Linking לאחר החלת מיגרציות ההרשאות. אלו הגדרות ספק; שינוי תבנית הסביבה אינו מפעיל אותן. באימייל נעשה שימוש ב־`updateUser`, אימות ואז בחירת סיסמה; הבעלות נשארת באותו UUID. כניסה לחשבון קיים משתמשת באסימון העברה חד־פעמי בעוגייה HttpOnly למשך 15 דקות וב־RPC אטומי. יש להשלים את הכניסה באותו דפדפן. [תיעוד Anonymous Sign-Ins](https://supabase.com/docs/guides/auth/auth-anonymous).

בתבנית Email Change של Supabase כוללים את קישור האימות וגם את `{{ .Token }}` כדי לאפשר הזנת קוד באותו דפדפן. מוודאים שלינק האימייל חוזר ל־`/auth/callback?next=/signup/complete`. OAuth יוצג רק אם הספק הוגדר ונבדק והדגל המתאים `AUTH_GOOGLE_ENABLED` או `AUTH_GITHUB_ENABLED` הוגדר `true`.

מחברים SMTP ייעודי, מאמתים שולח ורשומות DNS לפי ספק האימייל ובודקים שליחת אימייל לכתובת חיצונית. שירות האימייל המובנה של Supabase מוגבל ואינו תחליף להגדרת שליחה ציבורית. [Custom SMTP](https://supabase.com/docs/guides/auth/auth-smtp).

בדיקות חובה: אימות מהדפדפן המקורי, אימות ממכשיר אחר, קישור שנפתח פעמיים, קישור שפג תוקף, אימייל של חשבון קיים וחזרה להיסטוריית הראיון. הרשמה אינה מפנה ל־Onboarding או לאבחון חובה.

אם מפעילים Google/GitHub, כתובת החזרה אצל ספק ה־OAuth היא `https://PROJECT_REF.supabase.co/auth/v1/callback`; כתובת החזרה של האפליקציה ב־Supabase היא `/auth/callback` בדומיין שלך. מציגים כפתור ספק רק אחרי בדיקת התחברות וקישור אורח אליו. אין חובה להפעיל שני ספקים ביום הראשון אם מסלול האימייל עובד.

## 6. Vercel והגדרות הסביבה

1. מחברים את המאגר ואת ענף השחרור שנבדק.
2. בוחרים Next.js, שורש המאגר ו־Node.js 24 כפי שנעול בפרויקט.
3. משאירים את פקודת ה־build מ־`vercel.json`.
4. מזינים ב־Environment Variables את הערכים מ־[תבנית Production](../deploy/production.env.example), אחרי החלפת כתובות דמה ומילוי מפתחות.
5. ב־Production מגדירים `NEXT_PUBLIC_APP_URL` לדומיין HTTPS הקנוני ללא לוכסן בסוף.
6. ב־Preview לא מגדירים אותו; התשתית הקיימת משתמשת בכתובת הפריסה. מזינים בו פרטי Supabase ו־AI של Staging בלבד.
7. פורשים מחדש אחרי שינוי משתנים, כדי שגם משתני לקוח שנקבעים בבנייה יתעדכנו.

רק כתובת האפליקציה, כתובת Supabase והמפתח הציבורי מקבלים קידומת `NEXT_PUBLIC_`. מפתחות Gemini/OpenAI אינם מקבלים אותה. המפתח הציבורי של Supabase נשען על RLS; הוא אינו מפתח ניהול.

להרצת בדיקת הסביבה המקומית אפשר ליצור קובץ פרטי שה־Git מתעלם ממנו:

```powershell
Copy-Item -LiteralPath 'deploy/production.env.example' -Destination '.env.production.local'
```

עושים זאת רק אם קובץ היעד עדיין אינו קיים, כדי לא לדרוס הגדרות. ממלאים בו ערכים אמיתיים באופן פרטי ואז בודקים:

```powershell
node --env-file=.env.production.local scripts/check-production-env.mjs
```

הבודק הרגיל משתמש ב־process environment; הוא אינו טוען לבד את קובץ `.env.production.local`. ב־Vercel המשתנים מוזרקים לסביבה אוטומטית. אין להדפיס את תוכן קובץ הסודות או לצרף אותו ל־commit.

`SUPABASE_SERVICE_ROLE_KEY` נדרש כעת לניקוי המתוזמן בלבד. מגדירים אותו ואת `CRON_SECRET` אקראי באורך 32 תווים לפחות כמשתני שרת. אין להוסיף להם `NEXT_PUBLIC_`. שיוך ראיון לחשבון נעשה עם זהות המשתמש והוכחת האורח, ללא מפתח מנהל.

## 7. Domain ו־DNS

לאחר רכישת הדומיין מוסיפים אותו לפרויקט ב־Vercel תחת Settings → Domains. מעתיקים לרשם הדומיין את רשומות ה־DNS המדויקות שמציג הפרויקט. אין להעתיק IP או CNAME קבוע מדוגמה כללית. מוסיפים גם את גרסת `www` אם משתמשים בה ומגדירים הפניה לכתובת קנונית אחת. [הוספת דומיין ב־Vercel](https://vercel.com/docs/domains/working-with-domains/add-a-domain).

שומרים רשומות אימייל קיימות, ולא משנים nameservers בלי להעביר את הרשומות שצריך לשמר. ממתינים לאישור הדומיין ולתעודת HTTPS תקינה, מעדכנים את `NEXT_PUBLIC_APP_URL` ואת כתובות Auth ומבצעים פריסה מחדש.

לאחר המעבר בודקים שהלינק הציבורי נפתח בחלון פרטי ללא כניסה ל־Vercel וללא סיסמת הגנת פריסה. מסירים הגנת גישה מהגרסה הציבורית רק לאחר שהשחרור עבר את בדיקות הקבלה. Staging יכול להישאר מוגן.

## 9. מגבלות שימוש, עלות וניטור

לפני פתיחת ניסיון אנונימי בתשלום לספק AI מיישמים ניסיון אחד לזהות אורח, הגבלה על סשנים מקבילים, קצב יצירת טוקנים וחיבורים חוזרים ומכסה כוללת להשקה. אכיפה מתבצעת בשכבת שרת/DB משותפת, לא בזיכרון של פונקציה בודדת. הגבלת IP לא תהיה ההוכחה היחידה לזהות כדי לא לחסום קבוצת משתמשים באותה רשת.

ברירות המחדל ב־`interview_private.launch_limits`: 600 דקות ראיונות מוקצות ביום UTC ו־5 חיבורי קול במקביל, כולל חיבורים שממתינים להפעלה. הקצאות ספק מוגבלות ל־6 למשתמש ב־10 דקות ול־20 לראיון. המשוב מוגבל ל־60 בקשות ביום, 10 למשתמש ב־10 דקות ועד 3 ניסיונות להערכה, עם נעילה למשך 3 דקות. אלו תקרות אפליקטיביות ולא הבטחה לעלות כספית; מתאימים אותן לתקציב ולמכסות הספק לפני השיתוף.

באמצעות SQL Editor מנהלי אפשר לעצור הקצאות קול חדשות: `update interview_private.launch_limits set starts_enabled = false where id;`. ראיונות שכבר קיבלו הקצאה יכולים להתחבר שוב בכפוף למגבלות. הטבלאות הפרטיות אינן נגישות למשתמשי API.

מודדים: התחלה, הפעלת קול, זמן חיבור, כשלי ספק, חיבור מחדש, סיום, נטישה, הערכה זמנית, הצעת הרשמה וקישור מוצלח. לוגים מכילים מזהים וקודי סיבה בלבד, ללא טוקנים, סיסמאות, קוד או תמלול מלא.

`vercel.json` מפעיל ניקוי מדי יום ב־03:00 UTC. הוא מוחק תוכן אורח 7 ימים אחרי סיום/נטישה (בפועל בריצה היומית הבאה), הזמנות שלא הופעלו ופגו, וגם ראיונות שנעזבו בדפדפן ולא חזרו אליהם 7 ימים אחרי חלון הראיון. זהות האורח ורישום צריכת הניסיון נשמרים כדי שמחיקה לא תאפס זכאות. בודקים שה־Cron מופעל ב־Production, שהרצה לא מורשית מחזירה 401 ושהרצה מורשית מצליחה; אין הבטחת מחיקה בזמן מדויק לפני האימות.

## 10. בדיקת הפריסה והחלטת פתיחה לציבור

אחרי העלאת הגרסה מריצים עם הדומיין האמיתי:

```powershell
npm run verify:deployment -- https://YOUR_DOMAIN
```

זו בדיקת זמינות בסיסית בלבד. היא אינה מפעילה קול ואינה בודקת מסע אורח. תנאי פתיחה לציבור:

- [ ] כל המיגרציות של גרסת השחרור הוחלו ונבדקו ב־Staging וב־Production.
- [ ] הדומיין ו־HTTPS תקינים וכתובות Auth מובילות לדומיין הנכון.
- [ ] חלון פרטי מציג התחלת ראיון ללא הרשמה ואבחון.
- [ ] ראיון ראשון אמיתי הושלם באנגלית ובעברית, עם שיחות וקוד שנשמרו.
- [ ] המראיין הנוח והקשוח וה־Follow-up פועלים כפי שהוגדרו באפיון.
- [ ] רענון, ניתוק, כשל לפני קול ושתי לשוניות אינם גורמים לאובדן או להכפלת ניסיון.
- [ ] לאחר סיום/נטישה מופיעה הרשמה; קישור אימייל/חשבון קיים שומר את הראיון.
- [ ] ראיון שני לאורח נחסם גם בגישה ישירה; משתמש רשום יכול להמשיך בלי אבחון.
- [ ] משתמש אחר אינו קורא או משנה את הראיון, כולל בבדיקות RLS של אורחים אמיתיים.
- [ ] ספק AI ומערכת SMTP עובדים מול משתמשים חיצוניים, ולא רק חשבונות המפתח.
- [ ] מכסות שימוש, התראות, תהליך ניקוי ובדיקת סודות עברו אימות.
- [ ] זמינות הסיכום נבדקה גם אחרי שהמראיין סגר את הקול בעצמו.

משתפים את הקישור הראשי של הדומיין רק אחרי שכל התנאים הרלוונטיים עברו. בדיקת `health` ירוקה לבדה אינה החלטת השקה.

## 11. חזרה מגרסה תקולה

שומרים גרסת אפליקציה קודמת שנבדקה וגיבוי מתאים של בסיס הנתונים. אם יש תקלה עוצרים כניסות חדשות באמצעות מנגנון שרת מתוכנן; לא משתמשים בכיבוי מצב הבחירה כתחליף, כי הוא משנה את האלגוריתם ל־Learning.

שחזור גרסת Vercel אינו מחזיר לאחור מיגרציות. מתקנים סכמה במיגרציה חדשה ותואמת; לא מאפסים Production ולא מוחקים היסטוריית משתמשים. מנגנון עצירת התחלות צריך להשאיר סיכומים נגישים ולא לנתק ראיונות פעילים ללא צורך.

## 12. מה להביא לשלב החיבור

שם הדומיין שנרכש, בחירת פרויקטי Vercel/Supabase, הגדרת מפתח AI בתוך שירות הסודות, ספק אימייל ותקציב שימוש רצוי. את הסודות מכניסים ישירות בהגדרות השירותים. הקוד מוכן לשלב החיבור והבדיקות בסביבת Staging.
